## Chapter 2: Privileged Access: PIM, Managed Identities & RBAC — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | PIM: eligible assignment vs active assignment? | Eligible = requires activation (MFA, justification, optional approval) before the permission is usable. Active = permission granted immediately, no activation step. Exam tip: eligible assignments reduce standing privileged access risk. |
| 2 | Max PIM role activation duration range? | 1–24 hours, configurable per role; 8 hours is the common default. Exam tip: activation is always time-bound and auto-expires. |
| 3 | System-assigned vs user-assigned managed identity — lifecycle? | System-assigned: 1:1 with its resource, deleted automatically when the resource is deleted. User-assigned: standalone Azure resource, attach to many resources (many:1), independent lifecycle. Exam tip: choose user-assigned to share an identity across multiple resources. |
| 4 | Can a system-assigned managed identity be reused by multiple resources? | No — it is strictly 1:1 with the single resource it was created for. Use a user-assigned managed identity for shared/reusable scenarios. |
| 5 | Azure RBAC scope hierarchy, top to bottom? | Management Group > Subscription > Resource Group > Resource. Permissions inherit downward through the hierarchy. Exam tip: assign at the highest common scope needed to minimize role assignment sprawl. |
| 6 | Entra ID roles vs Azure RBAC roles — what does each control? | Entra ID roles = directory resources (users, groups, app registrations, licenses). Azure RBAC = Azure resources (VMs, storage, networking). Exam tip: they're separate systems — a Global Administrator does not automatically get Azure resource-level access. |
| 7 | Azure Policy: definition vs initiative vs assignment? | Definition = a single rule (e.g., allowed regions). Initiative = a grouped set of definitions targeting a compliance goal. Assignment = applying a definition or initiative to a specific scope. Exam tip: initiatives simplify managing related policies as one unit. |
| 8 | Azure Policy effects: Deny vs Audit vs Append vs DeployIfNotExists? | Deny = blocks non-compliant resource creation. Audit = logs non-compliance but allows creation. Append = adds fields/tags during creation without blocking. DeployIfNotExists = triggers remediation deployment of an associated resource if missing. Exam tip: Append never fails deployment; Deny always can. |
| 9 | Azure management group hierarchy depth limit? | Maximum 6 levels of management groups, not counting the root level or the subscription level itself. Exam tip: used to apply policy/RBAC inheritance at scale across many subscriptions. |
| 10 | Service principal vs app registration — difference? | App registration = the global definition of the application (created in its home tenant). Service principal = the local identity/instance object used to grant that app access within a specific tenant. Exam tip: one app registration can have a service principal in each tenant it's used in. |
| 11 | Best auth method for a workload to avoid storing credentials in code? | Managed identity (system- or user-assigned). Exam tip: eliminates secret storage, rotation, and leakage risk compared to a service principal with a client secret. |
| 12 | What PIM activation requirements can be enforced per role? | MFA, justification/reason, ticket number, designated approver approval, and a bounded maximum activation duration. Exam tip: all are configurable independently in the role's PIM settings. |
