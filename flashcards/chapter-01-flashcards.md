## Chapter 1: Entra ID Identity Fundamentals & Conditional Access — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | How many break-glass emergency access accounts does Microsoft recommend, minimum? | At least 2, cloud-only, excluded from all Conditional Access policies. Exam tip: they must never depend on MFA registration or federation that could fail. |
| 2 | Which Entra ID license tier is required for Identity Protection risk-based Conditional Access? | Microsoft Entra ID P2. Exam tip: P1 gives you standard Conditional Access; P2 adds risk detections and risk-based policies. |
| 3 | FIDO2 security key vs Microsoft Authenticator push — which is phishing-resistant? | FIDO2 security keys are phishing-resistant (origin-bound public key crypto). Authenticator push without number matching is more vulnerable to MFA fatigue/AiTM proxy attacks. Exam tip: high-security scenarios point to FIDO2. |
| 4 | Sign-in risk vs user risk — what's the difference? | Sign-in risk = probability THIS session is compromised (real-time, e.g., anonymous IP, atypical travel). User risk = probability the IDENTITY itself is compromised (e.g., leaked credentials). Exam tip: user risk → force password change; sign-in risk → require MFA. |
| 5 | Named locations: IP-range based vs country/region based — what determines country/region? | Country/region locations can be determined by IP address mapping (default) or GPS coordinates (if configured to require GPS-based determination via the Authenticator app). Exam tip: GPS-based is more accurate but requires user location permission. |
| 6 | PowerShell/Graph SDK cmdlet to create a new Conditional Access policy | New-MgIdentityConditionalAccessPolicy. Exam tip: uses Microsoft Graph PowerShell SDK; legacy AzureAD module is deprecated for CA management. |
| 7 | Three core components of every Conditional Access policy | Assignments (who/what apps), Conditions (risk, location, device platform, client apps), Access Controls (grant/block/session). Exam tip: policy = 'if conditions match assignment, then apply controls'. |
| 8 | Break-glass account architecture best practice checklist | Cloud-only (not synced), excluded from ALL CA policies, unique strong long password stored securely (e.g., sealed/physical safe), NOT registered for standard MFA methods tied to a device, sign-in activity monitored via alert. Exam tip: exclusion group must be referenced in every CA policy. |
| 9 | Security Defaults MFA enforcement model | All-or-nothing: enforces MFA registration for all users and requires MFA for admins/risky sign-ins tenant-wide, no granular exclusions or conditions. Exam tip: mutually exclusive with custom Conditional Access policies. |
| 10 | Identity Protection risk levels available for both sign-in risk and user risk | Low, Medium, High. Exam tip: policies are typically scoped as 'X and above' (e.g., Medium and above) rather than a single exact level. |
| 11 | What replaced the legacy per-user MFA service settings and SSPR authentication method configuration? | The unified Authentication Methods policy in Entra ID — single location to enable/configure Authenticator, FIDO2, SMS, voice, OATH tokens, etc. Exam tip: legacy MFA Service Settings page is being retired in favor of this policy. |
| 12 | Conditional Access grant control: multiple controls selected — AND vs OR | Admin chooses 'Require all the selected controls' (AND) or 'Require one of the selected controls' (OR) when multiple grant controls (e.g., MFA + compliant device) are configured. Exam tip: exam scenarios test which logic satisfies a stated requirement. |
