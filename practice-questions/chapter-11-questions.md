## Chapter 11: Microsoft Sentinel & Securing AI Workloads — Practice Questions

**Q1.** A SOC needs to detect impossible-travel sign-ins within 1 minute of ingestion, using a single KQL query against the SigninLogs table with no joins. Which Microsoft Sentinel analytics rule type should be configured?

A) Scheduled rule set to run every 5 minutes
B) Fusion rule
C) Microsoft Security rule
D) Near-real-time (NRT) rule

<details>
<summary>Answer</summary>

**Correct: D**

NRT rules execute every 1 minute against a single table with no joins, giving the fastest possible detection latency in Sentinel.

**Why the others are wrong:**
- Scheduled rules have a minimum frequency of 5 minutes, which is too slow for the sub-minute requirement.
- Fusion rules correlate multiple alert types across stages of an attack using ML — they are not for single-table, low-latency detections.
- Microsoft Security rules simply mirror alerts already generated by connected Microsoft products; they don't run custom KQL.

> ⚠️ Frequently missed on the exam — read the options carefully.

</details>

**Q2.** A security lead wants an incident's owner automatically assigned and a specific playbook launched only when the incident severity is High and the title contains 'Ransomware', without editing the playbook itself. What should be created?

A) Modify the playbook's trigger conditions in Logic Apps
B) A scheduled analytics rule with an attached automation option
C) A workbook with an automation tab
D) An automation rule with matching conditions and actions to assign owner and run the playbook

<details>
<summary>Answer</summary>

**Correct: D**

Automation rules centralize triggering conditions (severity, title, tags) and actions (assign owner, run playbook, close incident) without touching the playbook logic.

**Why the others are wrong:**
- Editing the playbook trigger mixes business logic into the Logic App and doesn't scale across multiple rules.
- Analytics rules generate alerts/incidents; they don't natively hold conditional owner-assignment logic — that belongs to automation rules.
- Workbooks are for visualization only and have no automation capability.

</details>

**Q3.** You are building a playbook that must run automatically whenever a new Sentinel incident is created, including access to all correlated alerts and entities. Which Logic Apps trigger should you use?

A) Microsoft Sentinel Alert trigger (legacy)
B) Microsoft Sentinel Incident trigger
C) HTTP request trigger
D) Recurrence trigger

<details>
<summary>Answer</summary>

**Correct: B**

The Incident trigger is the current recommended trigger, exposing the full incident object including all correlated alerts and entities for automation.

**Why the others are wrong:**
- The Alert trigger is the legacy trigger and does not expose incident-level context; Microsoft recommends migrating away from it.
- HTTP trigger requires manual invocation via API call and isn't fired automatically by Sentinel.
- Recurrence trigger runs on a schedule, not in response to incident creation.

> ⚠️ Frequently missed on the exam — read the options carefully.

</details>

**Q4.** A company's Azure OpenAI-based chatbot accepts user-uploaded documents. Attackers embed hidden instructions in those documents to override the system prompt. Which capability should the security team enable to detect this?

A) Microsoft Purview DLP policy
B) Azure AI Content Safety Prompt Shields
C) Microsoft Defender for Cloud Apps Cloud Discovery
D) Azure Firewall Premium

<details>
<summary>Answer</summary>

**Correct: B**

Prompt Shields in Azure AI Content Safety specifically detects both direct (user prompt) and indirect (document/content-embedded, XPIA) prompt injection attempts.

**Why the others are wrong:**
- Purview DLP protects sensitive data exfiltration/labeling but does not analyze prompt content for injection attacks.
- Cloud App Discovery identifies shadow AI app usage, not injection payloads inside document content.
- Azure Firewall filters network traffic and has no awareness of LLM prompt semantics.

> ⚠️ Frequently missed on the exam — read the options carefully.

</details>

**Q5.** Security leadership wants visibility into which generative AI web apps employees are using without organizational sanction. Which service provides this discovery?

A) Microsoft Defender for Cloud Apps Cloud Discovery
B) Microsoft Purview DSPM for AI
C) Microsoft Sentinel analytics rules
D) Azure AI Content Safety

<details>
<summary>Answer</summary>

**Correct: A**

Defender for Cloud Apps Cloud Discovery analyzes network/proxy logs to catalog shadow AI/SaaS app usage, including risk scoring for generative AI apps.

**Why the others are wrong:**
- DSPM for AI monitors data exposure risk within sanctioned Copilot/AI interactions, not general shadow-app discovery.
- Sentinel analytics rules detect threats from ingested log sources; they don't perform app discovery on their own.
- AI Content Safety filters harmful/injected content in a deployed AI app — it doesn't discover unsanctioned apps.

</details>

**Q6.** Which statement correctly distinguishes Microsoft Purview DSPM for AI from Azure AI Content Safety Prompt Shields?

A) DSPM for AI blocks jailbreak prompts in real time; Prompt Shields reports on oversharing of sensitive data
B) DSPM for AI monitors sensitive-data exposure and oversharing risk in AI interactions; Prompt Shields filters malicious prompt injection at inference time
C) Both services perform the identical function and are interchangeable
D) DSPM for AI is a Defender for Cloud feature; Prompt Shields is a Sentinel connector

<details>
<summary>Answer</summary>

**Correct: B**

DSPM for AI is a Purview data-security posture capability focused on sensitive data oversharing/labeling risk in Copilot and AI apps, while Prompt Shields is a content-safety guardrail that blocks/detects prompt injection during inference.

**Why the others are wrong:**
- This swaps the two functions — DSPM for AI does not block prompts in real time.
- They serve different purposes (data posture vs. content filtering) and are not interchangeable.
- DSPM for AI is a Purview capability, not Defender for Cloud; Prompt Shields is part of Azure AI Content Safety, not a Sentinel connector.

> ⚠️ Frequently missed on the exam — read the options carefully.

</details>

**Q7.** A SOC manager wants a dashboard showing MITRE ATT&CK-tagged incident trends over time with drill-down by tactic, built from KQL queries inside Sentinel. What should be created?

A) A workbook
B) An automation rule
C) A hunting query saved as a favorite
D) A notebook in Azure Machine Learning

<details>
<summary>Answer</summary>

**Correct: A**

Workbooks provide customizable, interactive KQL-based visualizations and dashboards natively within Sentinel/Azure Monitor.

**Why the others are wrong:**
- Automation rules handle incident response actions, not visualization.
- A saved hunting query returns tabular results for manual investigation, not an interactive visual dashboard.
- Notebooks (Jupyter) are used for advanced/ML-driven hunting workflows, not for standard exec-level dashboards.

</details>

**Q8.** What is the minimum query run frequency and the maximum lookback period supported by a Sentinel scheduled analytics rule?

A) 1 minute frequency, 7-day lookback
B) 15 minutes frequency, 30-day lookback
C) 1 hour frequency, 90-day lookback
D) 5 minutes frequency, 14-day lookback

<details>
<summary>Answer</summary>

**Correct: D**

Scheduled rules support a minimum run frequency of 5 minutes and a maximum lookback/query period of 14 days — commonly tested exact values.

**Why the others are wrong:**
- 1-minute frequency describes NRT rules, not scheduled rules, and the lookback figure is also wrong.
- 15 minutes/30 days are plausible-sounding but incorrect values not used by Sentinel scheduling limits.
- 1 hour/90 days far exceed the actual scheduled-rule configuration limits.

> ⚠️ Frequently missed on the exam — read the options carefully.

</details>
